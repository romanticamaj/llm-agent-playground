## 一句話

同一件事有四種接法 — 不是越底層越厲害，是你需要多大的鑰匙、扛不扛得起；往下掉之前，先問一句「這工具有沒有 CLI」。

## 三分鐘講稿

先講一個診所真的遇到的需求：讓 AI 每週自動把 Gmail 裡的發票附件抓下來、打包成一包。聽起來很單純吧？結果一路查下去，才發現這件小事會逼你穿過好幾層完全不同的接法。

第一層是 **connector（連接器）** —— 服務商幫你封裝好的東西：到設定裡點一下、跳出授權頁、按同意，就能用了。Gmail connector 能讀信、加 label、寫信、回信，日常需求其實很夠用。但翻它的能力清單，就是**沒有下載附件**這一項。

一開始會覺得「幹嘛鎖成這樣」，但你想一下就知道很合理 —— connector 要是全開，一般 user 弄出事誰負責？Claude 要負責嗎？Gmail 要負責嗎？沒有人要幫你負責，那就是你的風險要自管。所以服務商乾脆先幫你鎖起來。**connector 的本質，是別人幫你把風險封裝掉，代價是能力被鎖死。**

connector 做不到，先別急著裝 MCP —— **第一個該問的是：這工具有沒有 CLI？** CLI 是文字進、文字出，而 LLM 本來就是文字接龍引擎，這是它最自然的介面，不用再加一層協定。課堂實例：GitHub 我們本來只串到 connector、範圍受限；改成在 Claude Code 裡說一句「幫我串接 GitHub CLI」，瀏覽器授權完就拿到 `gh` —— 操作更底層、更有彈性。以後遇到新工具，直接把名字丟給 AI 說「幫我安裝」就好。**MCP 存在的意義，是給沒有 CLI 的工具用的**（Plaud、Notion 就沒有）。

沒有 CLI，才輪到 **MCP**。這裡要講清楚一件很多人搞混的事：**MCP 就是 connector 底下實作的協定**；反過來說，**connector 就是有服務商幫你封裝好的 MCP**。它們不是對立的東西，是同一條路的不同深度。官方 connector 缺你要的能力，你可以接第三方的 MCP server，甚至自己架一個 — 在本機 launch，拿到一個 127.0.0.1 開頭的網址，資料連外網都不用走。

代價是難度中等，而且**授權要你自己過**。課堂上就當場踩到 — 接 Notion 時授權卡在 callback 壞掉，怎麼點都回不來。這件事本身就是一課：**工具會壞，不要太相信別人寫的 code。** 你往下掉一層，就多接手一層別人不再幫你扛的東西。

再往下，最底層，是 **API key**。拿到 API key，你就等於天神了 —— 那把鑰匙能開你 Gmail 的一切。但你要自己去 Google Cloud Console 開專案、啟用 API、建 OAuth 憑證，流程繁瑣到會勸退很多人。

所以整條光譜長這樣：**Connector → CLI → MCP → API key**。它們其實都是 API，只是 package 過的 API — 差別只在誰幫你封裝、你拿到多大的權限、你扛多少風險。CLI 特別一點：它不是單純的「更底層」，是**剛好有 CLI 時的一條捷徑** —— 能力常常比 connector 大，設定卻比 MCP 便宜。代價是它要有 shell 這個口（見概念 23），而且是拿你本人的身分在跑。

判斷法則很簡單，而且方向是**由上往下**：**能用 connector 解決就不要往下掉**；connector 真的做不到（像那個下載附件打包），**先問這工具有沒有 CLI** —— 有就用 CLI，沒有才裝 MCP；MCP 還搞不定，才動 API key。每往下一層，能力變大、設定變繁瑣、風險從服務商身上移到你身上。

最後補一句：技術上當然可以直接從 API key 開始 — **你夠強可以啊，不是每個人都可以。** 對大多數人、大多數任務，這時候就很適合退回 connector，因為 connector 都幫你封起來了。

## 關鍵重點

- 四層是同一條光譜，不是四種技術：connector 是服務商封裝好的 MCP，MCP 底下還是 API — 它們都是 package 過的 API
- Connector：點開授權就能用，代價是能力被鎖死（Gmail connector 能讀信、加 label、寫信、回信，就是不能下載附件）— 鎖起來很合理，因為出事沒人幫你負責
- **CLI：LLM 最自然的介面** — 它本來就是文字接龍引擎，而 CLI 就是文字進、文字出，不用再加一層協定；有 CLI 就不必裝 MCP
- CLI 是捷徑不是深淵：能力常常比 connector 大、設定卻比 MCP 便宜；代價是要有 shell 這個口（見概念 23），而且拿你本人的身分在跑
- 課堂實例：GitHub 原本只串到 connector、範圍受限 → 在 Claude Code 說「幫我串接 GitHub CLI」、瀏覽器授權完拿到 `gh`，操作更底層、更有彈性
- MCP：**存在的意義是給沒有 CLI 的工具用的**（Plaud、Notion 就沒有）；接第三方或本機自架（127.0.0.1，不用走外網），難度中等、授權要自己過，而且工具會壞 — 別太相信別人寫的 code
- API key：最底層、「等於天神」，但要 Cloud 專案＋啟用 API＋OAuth 憑證，流程繁瑣、風險 100% 自負
- 判斷法則由上往下：能用 connector 就別往下掉 → 不夠用時**先問這工具有沒有 CLI** → 沒有 CLI 才裝 MCP → 都不行才動 API key
- 每往下一層＝能力變大、設定變繁瑣、風險從服務商移到你身上 — 選的不是「厲害」，是「你扛不扛得起」

## 互動示範構想

一個「任務 × 四層軌道」的對照台。上方是五個任務按鈕：讀最新 10 封信／幫信件加標籤／下載附件打包到資料夾／每週自動排程跑／把 code 推上 private repo。下方是四條並排的層級軌道：Connector、CLI、MCP、API Key，每條軌道右邊掛著三根代價量表（設定成本、權限範圍、風險自負）。

點任何一個任務，四條軌道即時亮燈：綠燈＝做得到、黃燈＝做得到但有附帶條件、紅燈＝這一層根本沒有這個能力，並在燈旁寫出理由（例如 connector 那格會攤開它的工具清單，讓你親眼看到「下載附件」不在裡面；CLI 那格則寫出「這個工具到底有沒有官方 CLI」）。

導演節奏：先用「讀信、加標籤」證明 connector 全包（三根量表都很低，風險條寫「服務商扛」）→ 切到「下載附件打包」，connector 那格變紅、清單抖動、標出缺口 → **掉下一層之前先演出那個分支：「有沒有 CLI？」** 切到 GitHub 那題，connector 那格也是紅的（範圍受限，push 這種底層操作不在裡面），CLI 軌道整條亮起、旁邊打出 `gh` 的字元流（文字進、文字出）→ 回到 Gmail 這題，CLI 軌道熄成紅燈（Gmail 沒有官方 CLI），這時才輪到 MCP 亮起，量表跟著長高、風險條從「服務商扛」翻成「一半自負」→ 再掉到 API Key，全綠但量表全滿、風險條寫「100% 自負」→ 最後開放 sandbox，讓使用者自由切任務、自己讀出「能用 connector 就別往下掉、要掉之前先問有沒有 CLI」這條心法。

## 課堂提問

- 你現在最想叫 AI 做的那件事，connector 夠不夠？你有真的去翻過它的能力清單嗎？
- 你天天在用的那幾個工具，哪些有 CLI、哪些沒有？你有沒有直接問過 AI「這個有 CLI 嗎，幫我裝」？
- 「connector 全開，一般 user 弄出事誰負責？」— 這個問題怎麼影響你選哪一層？
- 你手上有哪個任務，是真的值得你跑一趟 Google Cloud Console 去申請 API key 的？哪些其實不值得？
