## 一句話

你證明不了 agent 永遠不會亂講 — 但你可以把每一次發現的亂講，變成一條不准再犯的 regression test。

## 三分鐘講稿

先講一個很好笑但很真實的場景。客服機器人本該回答產品問題，結果有人丟一題數學給它，它就開始解了；再問它某支股票會不會賺，它也開始幫人分析起來。非決定性的輸出，你要怎麼確保它總是符合預期？

問題的根，軟體工程裡有個名字，叫 Test Oracle Problem，已經被討論二十幾年。寫過測試的都知道，1 + 1 就必須等於 2 — 輸入固定、輸出固定，對就是對。但你要怎麼測「這個回覆夠不夠禮貌」「這段摘要有沒有抓到重點」？根本指不出那個「權威判定者」在哪。而把生成式模型放進產品之後，這個問題直接被放大一百倍。

那怎麼辦？分兩種驗法。第一種 Deterministic — regex、字串比對、JSON schema、延遲門檻，這些有精確判定條件，便宜、快、可重現。第二種 Non-Deterministic — 語意層的「禮貌」「切題」沒有標準答案，就再找一個 LLM 來當裁判（LLM-as-a-Judge），它不是「你答對／答錯」的兩瞪眼，比較像評分機制。兩者真正的差別是成本：deterministic 是本機檢查，judge 每一條都是一次外部 API call。所以策略很清楚 — 能用 deterministic 就用，只有語意層才降級到 judge。

但這裡有兩個超重要的提醒。第一，assertion 過了不代表整段回答是對的。舉個很賤的例子：「我不能提供投資建議。不過這支股票基本面很好，可以買，快！」— 因為它說了「不能提供」，regex 就以為過了，但😂。第二，LLM 是機率性的，跑一次過了不代表什麼。要看的是「通過率」，不是單次有沒有通過。

最後收在整套心法。這套流程能「長大」是關鍵字 — 每次你發現機器人講了不該講的話，那就是一條新的 test case，config 會跟著產品一起長。你改不掉「模型會不會亂講」這件非決定性的事，但你可以在外面包一套決定性的執行流程：固定測試案例、記錄結果、把已知錯誤變成 regression。它不能證明 agent 永遠不出錯，只能保證同一種錯不要默默回來第二次。

還有一件跟上一章接得很緊的事：真正不該讓 agent 看到的東西，不要只靠一句「你不可以說出去」。Promptfoo 是驗證，不是隔離 — 它幫你去撞那道牆，但牆還是要自己用架構設計。agent 拿不到的東西，它就吐不出來，這比任何 prompt 都可靠。

## 關鍵重點

- Test Oracle Problem：語意品質沒有「權威正解」，LLM 進產品後被放大一百倍
- 兩種驗法：Deterministic（regex／schema／延遲，便宜可重現）vs. Non-Deterministic（LLM-as-a-Judge，貴）
- 成本導向策略：能 deterministic 就 deterministic，只有語意層才降級用 judge
- assertion 過 ≠ 整段對；LLM 是機率性的，要看「通過率」不是單次（用 `--repeat`、`--no-cache`）
- eval config 要「能長大」：每次抓到的亂講都變成一條新 regression，跟產品一起演化
- Eval 是驗證不是隔離 — 牆要用架構砌，eval 幫你去撞牆確認守住沒

## 互動示範構想

一個「機器人邊界」測試台。左邊是不斷長大的測試清單，使用者可以新增一條 test case（輸入問題 ＋ 期待 ＋ 驗法選 deterministic 或 judge）。中間放一隻 agent，按「跑一輪」它會回覆。右邊即時顯示每條 assert 的結果，並特別演示那個「賤例子」：一句話同時包含「我不能提供投資建議」跟「可以買，快！」— deterministic 的 regex 判「過」（綠燈誤判），切換到 judge 才判「不過」（紅燈）。再按「跑 10 次」，顯示通過率 7/10，強調「單次綠燈騙人，要看通過率」。每抓到一次亂講，一鍵「加入 regression」，清單就長一條。

## 課堂提問

- 你手上的 AI 應用，有哪些屬性可以用 deterministic 直接驗（格式、禁詞、範圍）？哪些只能靠 judge？
- 「assertion 過了不代表整段對」— 這個賤例子提醒你，寫測試時最容易騙過自己的是什麼？
- 為什麼「通過率」比「這次有沒有過」更誠實？這對你怎麼看 AI 的可靠度有什麼啟發？
