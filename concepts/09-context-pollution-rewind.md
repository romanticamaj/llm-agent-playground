## 一句話

不要在汙染的 context 上繼續修補 — 跳回乾淨的時間點，重新接龍。

## 三分鐘講稿

聊聊為什麼需要沒事多按「編輯」？只是因為修正錯字嗎？

AI 是文字接龍。所以當你輸入一個有問題的 prompt，或是 AI 給了一個不對的回應，然後你繼續往下聊、請它修正 — 你其實是在一段已經汙染的 context 上面繼續接龍。工程上有兩個詞：Context Pollution（上下文汙染）跟 Context Collision（上下文衝突）。一旦誤解被寫進 context，之後所有的回應都會帶著那個誤解往下走。有論文做過量化測試：跨多輪對話下指令，模型平均有 39% 的效能下滑 — 因為模型開始複製自己的前一個回應，而不是認真看新的指令。

這就是「編輯」真正在解決的問題。不管是 Claude 的 Edit、ChatGPT 的修改、還是 Claude Code 的 Rewind — 本質上都是同一件事：讓你跳回某個時間點，從那個點重新接龍。就像時光機。

工程上它在每一層都有實作：對話層是編輯訊息、截斷 context、重新生成；Coding Agent 層是 checkpoint — 在危險操作前先存檔，跑歪了直接跳回，跟打電動存檔一模一樣；Agent Framework 層是把每一步執行狀態序列化存起來，掛掉就從最後一個好狀態恢復。沒有 checkpoint 機制的 agent，只能算 toy。

更進階的是 Branching：Rewind 只是「回去」，Branching 是「回去之後，同時走兩條路」— 把 Git 的概念搬到對話上。分支式對話比線性對話的 context 縮減 58%，品質還更好，因為每條探索路徑都在自己乾淨的 context 裡跑。

講到 Git，剛好把這台時光機接回工程世界 —— 因為「編輯鈕」的原理，在工程世界就是**版本控制**。先把兩個常被搞混的東西分清楚：**git 是一個工具**，裝在你電腦上，本質就是程式碼的「記憶回溯器」—— 幫你的專案存檔、比對、跳回任何一個過去的版本；**GitHub 是一個網站**，是把 git 專案放上雲端的地方，你可以把它想成「git 界的 BMW」—— 一塊做得很漂亮的招牌。兩者常被當成同一個，其實**裝 git 不等於要用 GitHub**，你完全可以只在本機用 git、不碰任何網站。那 git 跟這章有什麼關係？一模一樣的道理：讓 AI 動手改 code 之前，**先 commit 一個節點**（等於存檔），讓它跑；跑歪了，直接退回上一個 commit —— 這就是對話層「編輯／rewind」在工程世界的對應版。checkpoint、rewind、branching，你在對話裡按的那顆時光機按鈕，工程師早就用 git 用了幾十年。

下次看到「編輯」按鈕，記住 — 它不是改錯字用的，它是會開啟平行宇宙的時光機。

## 關鍵重點

- Context Pollution：誤解一旦寫進 context，所有後續回應都帶著它走
- 多輪修補的效果遠不如跳回乾淨狀態重新生成（量化：平均 39% 效能下滑）
- Rewind 三層實作：Chat 編輯 / Agent checkpoint / Framework 狀態序列化
- Branching = 回去之後同時走兩條路，每條路都有乾淨的 context
- 核心原則：不要在汙染的 context 上修補，讓模型從乾淨狀態重新生成
- 工程版時光機就是 git：git 是工具（程式碼的記憶回溯器，本機存檔／跳回版本），GitHub 是網站（「git 界的 BMW」）
- AI 動手改 code 前先 commit 節點、跑歪退回 —— 編輯／rewind 在工程世界就是版本控制；裝 git 不等於要用 GitHub

## 互動示範構想

畫面是一棵對話樹。使用者跟模擬 AI 對話，其中一步故意選一個「錯誤理解」的回應 — 該節點變紅，之後每個新節點都帶著紅色暈染（汙染在傳播），品質分數持續下滑。然後使用者按「Rewind」，時間軸倒帶動畫回到紅色節點之前，從那裡長出一條乾淨的綠色新分支，品質分數回升。再按「Branch」可同時長兩條分支比較答案。紅綠對比 + 倒帶動畫，一眼看懂「時光機」。
