## 一句話

決定你迭代快慢的，不是你寫得多快，而是「驗證」那一段有多摩擦 — 摩擦越低，迭代越快。

## 三分鐘講稿

先給你一條公式，這是我這半年最有感的一句話：迭代速度 ≈ 1 / 驗證摩擦。

每個開發 loop 都是同一個模式：改 → 產出 → 驗證 → 學到東西 → 再改。而吃掉時間的，幾乎永遠是「驗證」那一段的摩擦。東西做好了，但「我親眼在真實環境看到它」中間隔著一堆手動步驟 — 搬檔、上傳、切裝置、連回另一台機器。步驟越多，你一次能驗證的越少、越晚，問題都拖到最後才知道。

講兩個我每天在用的例子。第一，我整條開發 loop 幾乎都在手機上跑完 — 手機串 coding agent、串 GitHub、接到 Vercel/Cloudflare 部署。驗證呢？入口掛上 Tailscale，本機跑起來的版本，我手機直接連進去看，確認沒問題就在手機上發布。從改、到看、到發，沒有一步是「先回到電腦前面」。第二，生圖／生影片／生音樂，我在那台機器上架一個預覽小網站，遠端連進去看效果，不滿意就繼續迭代 — 沒有上傳、沒有搬檔，人也不用坐在那台機器前。

重點其實不是 Tailscale，它只是個例子。真正要做的是：回頭看你自己的開發流程，找出摩擦最大的那一段（多數人就是卡在驗證），然後用任何塞得進這個 loop 的工具，把那段摩擦砍掉。能有效迭代的人，差別常常就在這裡。而且更進一步，我把「降摩擦」這件事本身也自動化 —— 一觸發驗證就自動生一個異地連得到的版本。friction 變成 rule。

把這件事推到極致，就是我說的兩個更大的框架。一個是「無限大 Engineering」— 一條 loop 把我從 turn-by-turn 執行裡移出去，另一條 loop 讓我人不在電腦前也能驗收，兩條接起來，我站在交點上邊掃地邊開發。另一個是 Remote Engineering：以前的 Remote Work 只是把你從公司的桌子搬到家裡的桌子，但 Remote Engineering 是讓你逐漸離開電腦桌 — 把原本需要人坐在機器前的操作，轉成 agent 能呼叫的工具；把原本需要人親眼確認的結果，轉成截圖、錄影、Log、測試報告。這兩件事做完，整個迭代就能遠端進行。

所以這一章談「視野」，第一件事就是這個心法：不要只想著把「寫」變快，要去把「驗證」變順。摩擦砍到趨近零，你的 loop 才可能放手、才走得到 autonomous、走得到一週工作四天。

## 關鍵重點

- 核心公式：迭代速度 ≈ 1 / 驗證摩擦 — 瓶頸幾乎永遠在「驗證」那一段
- 每個 loop 都是：改 → 產出 → 驗證 → 學到 → 再改；驗證步驟越多，問題越晚被發現
- 降摩擦的做法（Tailscale 只是例子）：遠端直接看本機版本、東西全留 local、不搬檔不上傳
- 把降摩擦本身也自動化：friction 變成 rule
- 更大的框架：把人移到兩條 loop 的交點（∞ Engineering）、逐漸離開電腦桌（Remote Engineering）
- 通則：把「人坐在機器前的操作」變成 agent 能呼叫的工具，把「親眼確認」變成截圖／錄影／Log

## 互動示範構想

一條可視化的開發 loop 跑道：改 → 產出 → 驗證 → 學到 → 再改，一顆小球繞圈跑。「驗證」那一段預設塞著好幾個障礙格（搬檔、上傳、切裝置、走回電腦），小球每經過一個就卡頓一下，上方碼表顯示一圈耗時。使用者可以逐一「移除」障礙（例如點掉「走回電腦」換成「手機 Tailscale 直連」），每移除一個，小球那段就變順、碼表數字掉下去，右上角的「迭代速度 = 1 / 摩擦」指針隨之往上跳。全部砍光時，loop 快到可以「放手自動跑」，解鎖一個「一週工作四天」的彩蛋。

## 課堂提問

- 回想你最近一個專案，「驗證」那一段有哪些手動步驟？哪一個摩擦最大？
- 如果把「降摩擦」變成一條自動觸發的規則（friction 變成 rule），你會先自動化哪個環節？
- 「Remote Work 是換張桌子，Remote Engineering 是離開桌子」— 你的工作有多少比例已經可以離開電腦桌？

> 從改、到看、到發，沒有一步是「先回到電腦前面」。
